🎟️ 1. Generación de la entrada (QR)

Cuando compras una entrada (web/app/kiosco):

El sistema crea un ticket único con datos como:
ID de la orden
ID del asiento
función (película, sala, hora)
usuario (opcional)
Luego genera un QR que puede contener:
Un ID único (UUID) → más común
O un token firmado (JWT) con la info embebida

👉 Buenas prácticas:

No meter toda la info sensible en el QR, mejor usar un ID y consultar backend
Firmar o encriptar el QR para evitar fraude

🧩 2. Arquitectura de microservicios

Un sistema moderno suele dividirse así:
Servicios principales:
Order Service → gestiona compras
Ticket Service → crea y administra tickets
Showtime Service → funciones, salas, horarios
User Service → usuarios
Notification Service → envía el QR (email/app)
Validation Service → escaneo y control de acceso

🔄 3. Sincronización entre microservicios

Se logra con eventos + APIs:

a) Flujo típico:
Usuario compra → Order Service
Order Service emite evento:
OrderConfirmed
Ticket Service escucha ese evento → genera ticket + QR
Ticket Service emite:
TicketCreated
Notification Service envía el QR al usuario

👉 Tecnologías comunes:

Kafka

📲 4. Validación del QR en el cine

Cuando escanean el código:

El lector (app o dispositivo) lee el QR
Envía el ID/token al Validation Service
Este:
Verifica firma/token
Consulta Ticket Service
Revisa estado:
válido ✅
ya usado ❌
expirado ❌
Si es válido:
Marca ticket como usado
Devuelve OK

⚡ 5. Consideraciones clave
🔒 Seguridad
Firmar QR (JWT o HMAC)
Evitar duplicados (idempotencia)
Protección contra reuso
⚡ Performance
Cache (Redis) para validación rápida
Validación offline (opcional en QR con firma)

📡 Consistencia
Eventual consistency entre servicios
Uso de eventos como:
TicketValidated
TicketCancelled


🧱 7. Ejemplo de flujo completo
Compra → Order Service
        ↓ evento
Ticket Service → genera QR
        ↓ evento
Notification Service → envía QR

Entrada cine:
Scanner → Validation Service → Ticket Service
                        ↓
                marcar como usado


🚀 Recomendación práctica

Si estás diseñando esto:

Usa event-driven architecture
QR = ID + firma
Validación con cache + fallback DB
Mantén servicios stateless
Logging fuerte (auditoría de accesos)

Manejo de consistencia

Problema típico:
👉 dos scanners leen el mismo QR al mismo tiempo

Solución:
operación atómica en Redis

Ejemplo con Lua:
if redis.call("GET", key) == "valid" then
  redis.call("SET", key, "used")
  return 1
else
  return 0
end


7. Seguridad realista
JWT con expiración corta (ej: fin de la función)
Firma fuerte (RS256 recomendado)
Rotación de claves
Evitar exponer datos sensibles

NO lleva modo offline
